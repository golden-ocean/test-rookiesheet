构建可审计的
Sentinel access control

Sentinel 是一套面向 Rust 服务端的身份与访问管理参考架构：以领域驱动设计划分模块边界，以 CQRS 分离读写路径，用 PostgreSQL 承载领域状态、Redis 加速读模型。本档案记录它的架构决策、领域模型与接口约定。

01概览

访问控制是后台系统里最早长出、也最容易腐烂的一块。权限判断散落在各个控制器里，角色与菜单的关系只存在于某位早期成员的心中，等新人接手时，没人敢删除任何一行代码。

Sentinel 把这件事当作一个正式的架构问题来对待：用户、角色、权限、组织、字典各自成为独立的领域模块，模块之间只通过显式声明的端口通信。应用状态由 PgPool 持久化，读模型投影同步写入 RedisPool，两者在 AppState 中组装，由 server crate 统一接入 HTTP 层。

这份文档适合谁

即将接入 Sentinel 的后端工程师，以及准备改造现有权限体系的架构师。如果你只想先跑起来，建议直接跳到快速上手。

02设计原则

四条原则贯穿整个仓库。它们不是口号，每一条都能在代码里找到对应的强制约束。

  1. 显式建模，拒绝隐式约定

    每个领域概念都有独立的新类型 ID 与聚合根，跨模块引用必须显式转换，不允许裸 i64 在系统里流浪。

  2. 读写分离，各走各路

    命令经过领域模型保证不变量；查询绕过聚合直连读模型与缓存。两侧可以独立演进、独立优化、独立失效。

  3. 模块自治，胜过统一抽象

    每个 crate 自带错误类型、ID 定义与接口转换。shared 只提供真正通用的基础设施，不制造上帝抽象。

  4. 按需演进，不为未来买单

    审计、软删除、多租户、乐观锁在 shared 中预留位置，直到真实需求出现才落地实现。

03架构总览

系统按模块化单体组织：五个 crate 平级协作，server 只做组装，不承载任何业务逻辑。每个业务 crate 内部分为 application / domain / infrastructure / presentation 四层，层间单向依赖。

Crate职责关键抽象
iam账号、角色、权限与授权判定User, Role, Permission, Policy
org组织结构、岗位与成员关系Organization, Position, Membership
sys字典配置与枚举值管理Dictionary, DictionaryItem
serverHTTP 组装、中间件与进程生命周期Router, AppState
shared跨模块通用基础设施（占位）TypedId, Clock
模块之间禁止横向依赖

当 iam 需要组织信息时，通过 org 暴露的端口查询，而不是直接读取其内部表。这条约束由 CI 中的依赖检查强制执行。

04快速上手

三种安装方式任选其一。开发环境推荐容器方式，生产环境建议使用 Helm chart 部署。

启动前检查

  1. 准备依赖服务

    PostgreSQL 15 及以上，Redis 7 及以上。两者均为强依赖，没有内存降级模式。

  2. 执行数据库迁移

    sqlx migrate run 会创建全部领域表与读模型投影表，迁移脚本随版本发布，不支持跳过。

  3. 启动服务并验证

    cargo run -p server，访问 /healthz 返回 ok 即就绪。默认监听 8080。

05核心特性

四个特性定义了 Sentinel 与「把权限写死在 if 里」的方案之间的差距。

防腐分层

application 层只依赖 domain 声明的端口，SQLx 实体被限制在 infrastructure 内。领域模型对数据库细节零感知，换存储不需要动一行业务代码。

投影读模型

查询侧维护宽表投影，命中 Redis 时延中位数 1.2ms。缓存失效由领域事件驱动，不依赖定时清理。

细粒度授权

RBAC 角色叠加数据范围与字段级策略，判定逻辑集中在 domain，一条命令一个授权点。所有判定记录不可变审计事件。

可观测性

结构化日志、OpenTelemetry 链路追踪与审计事件流。每次授权判定都可回溯到具体角色、策略版本与请求 ID。

从零开始的最小闭环

创建角色 → 绑定权限 → 分配给用户 → 在命令入口调用授权点。四步之后，系统里不再有任何裸露的权限判断。
